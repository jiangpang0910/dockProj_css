# Backend

Data model, rule enforcement, REST API, and the legacy-import pipeline. Behavior is defined in
[manual.md](manual.md) (OP-xx and R1–R6); this file says how it is built.
The API contract (types + request schemas) lives in **[`shared/contract.ts`](shared/contract.ts)**, imported by both the route handlers and the UI. It is the source of truth; this file only describes it.

**Design rule:** `rules.ts` is pure. It takes a small `BookingStore` interface
(`overlapping(berthId, start, end, excludeId?)`, `vesselBookings(vesselId, start, end, excludeId?)`, `getBerth`, `getVessel`).
The SQL-backed service and the importer's in-memory staging store both implement it, so **manual booking and
import apply exactly the same code**.

## 2. Shared types

Dates are `"YYYY-MM-DD"` strings, compared lexicographically (which orders them correctly). Never use `Date` for
booking dates: `new Date("2026-03-05")` parses as UTC and shifts a day in some zones.

See **[`shared/contract.ts`](shared/contract.ts)**. Part 1 is the types that go over the wire. Part 2 is the zod schemas for every
request body and query. Shape errors → 400 `VALIDATION`; rule violations come from `rules.ts` → 409/422 (§4).

Key constants: `DATE_MIN` 1997-01-01, `DATE_MAX` 2050-12-31 (sanity bounds, all sources);
`SOFT_HORIZON_YEARS` 2 / `HARD_HORIZON_YEARS` 5 (manual bookings only, measured from `asOfDate`: past 2y → `FAR_FUTURE` warning, past 5y → `BEYOND_HORIZON` error);
`MAX_WINDOW_DAYS` 366 (read endpoints: how much one request may load).

## 3. Database

**See [database.md](database.md).** What backend code must know:

- **Everything is scoped to a project.** Every query on berth / vessel / booking / import filters on `project_id`.
  Every route under `/api/projects/:pid` first loads the project: 404 if it's unknown, 403 `FORBIDDEN` on a write to a
  template.
- **R1–R4 and R6 are also enforced by the database** (`CHECK`, `EXCLUDE`, triggers). `db/errors.ts` maps by
  `err.constraint`: `booking_no_overlap` → `OVERLAP`, `booking_vessel_once` → `VESSEL_DOUBLE_BERTHED`,
  `booking_fit` / `*_length_guard` → `VESSEL_TOO_LONG`, `booking_range_valid` → `INVALID_RANGE`,
  `booking_berth_fk` / `booking_vessel_fk` on delete → "still referenced". Reaching this path means `rules.ts` missed
  something, so return the 409/422 **and log it loudly**.
- **Every write is one transaction.** Keep the `pg.PoolClient` for the whole `BEGIN … COMMIT` and release it in `finally`.

## 4. Booking validation (`rules.ts`)

`validateBooking(input, store, { excludeId?, source }) → Violation[]` — collects **all** violations (not fail-fast), so the UI can show
everything at once. Order:

1. **R1** — both dates strictly valid, `end >= start`. → `INVALID_RANGE`. If the range is invalid, skip the date-based checks.
2. Occupant fields: vessel needs `vesselId`; event/closure need `title`. → `MISSING_FIELD`.
3. Berth exists and is active. → `BERTH_INACTIVE` (unknown berth → 404).
4. **Vessel length known?** If the vessel's `lengthFt` is null and `source === "manual"` → `VESSEL_LENGTH_UNKNOWN` (error). Imports skip this.
5. **R3** — vessel length > berth length (berths only) → `VESSEL_TOO_LONG` with `details { vesselLengthFt, berthLengthFt, shortByFt }`.
6. **R2** — `store.overlapping(...)` (berths only) → `OVERLAP` with `bookingIds`.
7. **R4** — `store.vesselBookings(...)` → `VESSEL_DOUBLE_BERTHED` with `bookingIds`.
8. **Horizon** (`source === "manual"` only; imports skip it) — `end > addYears(asOfDate, 5)` → `BEYOND_HORIZON` (error);
   otherwise `end > addYears(asOfDate, 2)` → `FAR_FUTURE` (warning: "Booking is N years out — typo?").
9. **Warning** — `end < settings.asOfDate` → `IN_PAST` (severity `warning`).

`ok` = no violation with severity `error`. The overlap query, as used by both the service and the trigger:

```sql
SELECT id, title, start_date, end_date FROM booking
WHERE berth_id = :berth AND status = 'confirmed' AND id <> :exclude
  AND start_date <= :end AND :start <= end_date
ORDER BY start_date;
```

### HTTP status mapping

| Situation | Status | `error.code` |
|---|---|---|
| Malformed body / bad query params (zod) | 400 | `VALIDATION` |
| Unknown id | 404 | `NOT_FOUND` |
| `OVERLAP` or `VESSEL_DOUBLE_BERTHED` (state of the schedule blocks it) | 409 | `CONFLICT` |
| `VESSEL_TOO_LONG`, `VESSEL_LENGTH_UNKNOWN`, `BERTH_INACTIVE`, `INVALID_RANGE`, `MISSING_FIELD`, `BEYOND_HORIZON` | 422 | `UNPROCESSABLE` |
| Both kinds at once | 409 | `CONFLICT` (all violations included) |
| `expectedVersion` doesn't match | 409 | `STALE_VERSION` |
| R6 (length edit would break bookings) | 409 | `CONFLICT`, `violations[].bookingIds` lists them |
| Write to a template project | 403 | `FORBIDDEN` |
| New project while at the cap | 503 | `UNAVAILABLE` |
| Anything else | 500 | `INTERNAL` |

```jsonc
// POST /api/projects/:pid/bookings  → 409
{ "error": { "code": "CONFLICT", "message": "Berth is already booked on 2 of those days.",
  "violations": [{ "code": "OVERLAP", "severity": "error",
                   "message": "North Pier West is held by R/V Golden Compass 2026-03-04 to 2026-03-06.",
                   "bookingIds": ["7f0c…"] }] } }
```

`POST …/bookings/validate` returns 200 with a `ValidationResult` — the violations are the *answer*, not an error.

Notes:

- **Create project.** `sample` / `defaults` call `clone_project(<template id>, name, origin)`, one statement
  (database.md §6). "Upload your own" is two calls: `POST /api/projects {start:"empty"}`, then `POST …/imports`.
  Cap: 300 non-template projects → 503 `UNAVAILABLE`.
- **Bookings read.** `GET /bookings` requires `from` and `to`. It returns bookings that touch the window, confirmed only
  unless `includeCancelled=true`.
- **Schedule read.** `GET /schedule` is the same query plus the berth list, so the grid needs one round trip. Default
  `from`/`to`: the month containing `Settings.asOfDate`.
- **Cancel** sets `status='cancelled'` and `version+1`. The berth is free again immediately.
- **PATCH booking** merges fields onto the existing row, then validates the *result* with `excludeId = id`.
- **Unique names** are per project and case-insensitive (`lower(name)`). A duplicate → 409 `CONFLICT`, and the message
  names the clash. Names are stored normalised: trimmed, single spaces, `OS/V` → `OSV`.
- **Create berth.** `kind: "berth"` needs `lengthFt > 0`; `kind: "section"` needs `lengthFt: null`. `kind` can't change
  after creation. It isn't in `BerthPatch`, and the DB's composite FK blocks it once the berth has bookings.
- **Delete berth / vessel** is a hard delete, allowed only when **no booking of any status** references it. Otherwise:
  409 `CONFLICT` with the count. For a berth, the UI then offers *deactivate* (`PATCH { active: false }`). The FKs back
  this up.
- **Import and deleted records.** Re-importing a file recreates vessels and berths the user had deleted, matched by name.
  That's consistent: the file says they exist.

### Availability

`GET …/availability?startDate&endDate&(vesselId|lengthFt)` — for each **active** berth:

- `conflicts` = the overlap query for the window (berths only; a section always has none that matter).
- `free` = `kind === 'section' || conflicts.length === 0`.
- `fits` = no length asked, or berth is a section, or `berth.lengthFt >= lengthFt`.
- `slackFt` = `berth.lengthFt - lengthFt` (null when either is missing).
- Sort: `free && fits` first; then by `slackFt` ascending (tightest fit first, nulls last); then `sortOrder`.

With `vesselId`, `lengthFt` is the vessel's length (422 `UNPROCESSABLE` if the vessel has none — the caller must supply `lengthFt` instead). Availability does not check R4 (vessel already booked elsewhere); `validate`/create will.

### Settings

`project.as_of_date` holds the override, if any. `GET` returns the override (`asOfSource: "override"`) or today's date
in the facility's zone (`"system"`). Compute that with an explicit zone (`America/New_York`), not the server's clock zone,
because Vercel runs in UTC. `PUT { asOfDate: null }` clears it. The sample template ships with `2019-07-01`.

## 6. Import pipeline

```
 .xlsx ──► pipeline/ (Python)                          ──► ParsedWorkbook JSON ──► import/stage.ts (TS)                 ──► staging tables
           "what does the file say?"                       shared/pipeline.ts      "what is allowed?"
           1 detect format (sheet names)                   zod-validated           1 planning window: drop rows outside
           2 parse: template tables | legacy grid                                  2 match berths/vessels (project + staged)
           3 classify each cell: regex first,                                      3 rules.ts, earliest-first, MemoryStore
             model only for what regex can't place                                 4 pass → staged row; fail → issue
           4 normalise names, merge ranges, attach lengths
```

**Split of work.** Python parses. It never decides whether a booking is *allowed*: it emits every row it could read,
with parse-level issues. TypeScript owns the planning window and the rules (`rules.ts`), so manual booking and import
still run the exact same rule code.

**Nothing is rejected wholesale.** An upload always produces a preview. Rows that pass are staged. Rows that read fine
but can't be placed (overlap, too long, double-berthed, no berth, berth inactive) become **conflicts** (§6.6). Cells that
couldn't be read properly become **issues**. Commit brings in the staged rows and opens the conflicts; nothing waits silently.

**Planning window.** `from` = the project's "today" at upload time (the anchor: *the earliest date you're planning
for*); `to` = the `planTo` field, default `from + HARD_HORIZON_YEARS`. A row is kept if it **touches** the window
(`start ≤ to && end ≥ from`, unclipped: a stay that began before `from` still occupies the berth). Everything else is
counted in `counts.outsideWindow` and skipped, and so are parse issues whose row lies outside the window, so planning
2008 isn't buried under 1998's problems. Issues without a row (e.g. `HEADER_YEAR_MISMATCH`) are kept. Seeding the
sample template uses the full range (`DATE_MIN…DATE_MAX`).

**Where Python runs.**
- **Production:** a second Vercel project from the same repo (Root Directory `pipeline/`, Python runtime), exposing
  `POST /api/parse` (body: the file bytes; header `x-parser-secret: $PARSER_SECRET`) → `ParsedWorkbook`. The Next app
  calls it at `PARSER_URL`.
- **Locally, in tests and seeding:** no server. `import/parser.ts` spawns `python3 -m pipeline.cli --stdin` and reads
  JSON from stdout.

**The model step (optional).** Regex classifies ~95% of cells (prefixes `R/V M/V …` → vessel; keyword lists → closure /
event / operational note). What's left (odd free text like "Sea Scouts overnight" or "Hull survey – yard") goes to a
small hosted model, **Claude Haiku 4.5**. There is one batched request per upload, containing only unique leftover
strings, at temperature 0, with strict JSON output (`{text → vessel|event|closure|note|unknown}`). Model-classified rows
carry `classifiedBy: "model"` plus an info issue `MODEL_CLASSIFIED`, so a person can check them. No `ANTHROPIC_API_KEY`
means the step is skipped and those cells stay `UNPARSEABLE_CELL`: the pipeline never *needs* the model. The model only
ever labels text; dates, berths and lengths always come from regex and the grid structure.

### The template (`public/dock-template.xlsx`): "our standard"

Plain tables, one header row per sheet, one record per row. Every sheet is optional. You can upload just Berths and
Vessels to configure a project, or just Bookings for a project that already has its fleet.

| Sheet | Columns (header text must match, case-insensitive) | Rules |
|---|---|---|
| `Berths` | `Name` · `Kind` · `Length (ft)` · `Order` | Kind is `berth` or `section`. Length is required for a berth and must be blank for a section. Order is optional; default is file order |
| `Vessels` | `Name` · `Length (ft)` · `Draft (ft)` · `Operator` · `Notes` | Name is required. A blank length means "unknown", like legacy vessels, and blocks manual booking until filled in |
| `Bookings` | `Berth` · `Type` · `Vessel / Title` · `Start` · `End` · `Notes` | Type is `vessel`, `event` or `closure`. Berth must name a berth in this file or already in the project. A vessel name not found anywhere is created with an unknown length. Start and End (inclusive) are Excel date cells or `YYYY-MM-DD` text |

- A wrong header row → `TEMPLATE_BAD_HEADER` (error). That sheet is skipped and the others still import.
- A bad cell (kind, length, type, date) → `INVALID_VALUE` (error), with sheet and cell (`Bookings · D12`). The row is skipped.
- The same name twice in the file → `DUPLICATE_NAME` (warning); the first is kept.
- A name that already exists in the project → `DUPLICATE_EXISTING` (info). The existing record is used, not overwritten.
- **Excel dates:** exceljs returns a date cell as a JS `Date` at **UTC** midnight. Read it with `getUTCFullYear/Month/Date`.
  Local getters shift it by a day in the Americas.

The generator (`npm run template:build`) adds a Kind/Type dropdown (data validation), a frozen header row, and one
example row per sheet that the parser skips because its Name starts with `e.g.`.

### Legacy grid

Turns the original year-per-sheet workbook into staged rows plus issues explaining everything else. `pipeline/grid.py`
grew out of the `backend/parse.py` prototype. Berth labels shaped `Name - 410'` (and
the two section labels) **stage a berth** if the project doesn't have one by that name. So a legacy upload into an
*empty* project works, and it builds the same 8 berths the defaults have.

**Stage 1 — parse the grid** (`pipeline/grid.py`). Only sheets whose name is a 4-digit year are schedules; `8YR Dock Summary`, `Science`, `Yachts`, `Tours` are not (Science/Yachts feed stage 2).

- A **month block** starts at a row whose column A is a month name (with or without a year, e.g. `JANUARY 2010` or `January`). It runs to the next month header.
- **Day columns:** find the column holding the number `1` in the block's header rows (the numbered row is the header row, or one or two below it). Day *n* is that column + *n*−1. **Do not** trust the other day numbers — old sheets only number day 1.
- **Year of a block:** don't trust the label alone (the 2010 sheet has "NOVEMBER 2018" and "DECEMBER 2018"). Start from the sheet year and advance by sequence (year +1 when the month number decreases); check the weekday letters (`M T W TR F S S`) against the real calendar. A contradiction → issue `HEADER_YEAR_MISMATCH` (info).
- **Berth rows** are the rows under the header whose column A looks like `Name - 410'`. Also recognise the section rows `North Finger Piers:` and `Small craft slips (institution boats)`. Anything on a row with **no label** has no berth → `NO_BERTH`.
- **A booking cell** is any non-empty text cell in a berth row at a day column. A **merged range** spans several days. Ignore the weekday-letter cells and numbers.
- **Cells before day 1** (in the blank columns) are carry-overs from the previous month → `OUTSIDE_MONTH_COLUMNS`.
- **Carry-over December:** sheets 2002–2004 open with a copy of the previous December. Drop it → `DUPLICATE_CARRYOVER` (info).

**Stage 2 — normalise.**

- Trim, collapse whitespace, compare names case-insensitively (`lower(name)` after normalising); display name = first spelling seen, title-cased consistently.
- Fix known prefix typos (`OS/V` → `OSV`).
- Classify text: **vessel** if it starts with `R/V M/V M/Y S/V S/Y F/V OSV TUG BARGE`; else **closure** on keywords (`MAINTENANCE REBUILD REPAIR WORK CLOSED NO DOCKING TEST PAVING INSPECTION RESTRICTED CRANE UTILITY BOLLARD`);
  else **event** on keywords (`COMMUNITY CAMPUS HOLIDAY RACE TOUR OPEN HOUSE STROLL RECEPTION DRILL TRAINING FILM`); else **operational note** on keywords (`ETA ARRIV DEPART ETD FUEL BUNKERING WATER TOUCH DELAY PROVISION LOAD WIRE RETURNS EMERGENCY PUMP`) → `ANNOTATION_SKIPPED`. Unmatched text → `UNPARSEABLE_CELL` with `row` filled so it can be created by hand.
- Read `Science` and `Yachts` for cells shaped `Name NN'` and build a `name → lengthFt` map. Only ~19 scheduled vessels match; the rest get `lengthFt = null`.
- **Coalesce:** same berth + same name + touching or overlapping day ranges (including across month boundaries) → one booking. (Ambiguity: two unmerged adjacent cells could in principle be two stays; treat as one.)

**Stage 3 — apply the rules.**

1. Map the berth label to a berth: an existing one in the project, or one staged from this file. A row with no label → `NO_BERTH`.
2. Sort rows by `(startDate, endDate)`. Feed them one at a time through the **same `validateBooking`** using an in-memory `BookingStore` seeded with the project's *existing* live bookings (loaded once per berth, not per row) plus everything accepted so far; use `source: "import"` (length-unknown allowed, no `IN_PAST`).
3. A row identical to an existing confirmed booking (same berth, title, dates) → `DUPLICATE_EXISTING` (info), skip. This is what makes re-importing the same file safe.
4. Otherwise: no `error` violations → **stage it**; a placement violation → a staged **conflict** typed by it (`OVERLAP`, `VESSEL_TOO_LONG`, `VESSEL_DOUBLE_BERTHED`, `BERTH_INACTIVE`); bad data (`INVALID_RANGE`, `MISSING_FIELD`) → an `INVALID_VALUE` issue. Rows with no berth (or an unknown one) → a `NO_BERTH` conflict. Because rows are processed earliest-first, the earlier booking wins an overlap. A conflict's vessel is still staged, so placing it later needs nothing else.
5. Store the `ImportRun` with counts, return it. **Nothing is written to `booking` yet.**

**Commit** (`POST …/imports/:id/commit`) is one transaction:
1. Insert the staged berths.
2. Insert the staged vessels, matching existing ones by `lower(name)`.
3. Insert the staged bookings with `source='import'`, pointing each at its real or new berth and vessel.
4. Open the staged conflicts, resolving their berth / vessel names to the now-real rows.
5. Set the import's status to `committed`.

The DB constraints re-check every row. If any fires, the whole commit rolls back, which must never happen in tests. A second commit → 409.

**Resolve** (`POST /imports/:id/issues/:issueId/resolve`):
- `create_booking { berthId, vesselLengthFt? }` — builds a `BookingInput` from the issue's `row` (vessel found or created by `lower(name)`, `vesselLengthFt` sets its length if given), runs the normal create path with `source:"import"`. Rule failures return the usual 409/422 and the issue stays open.
- `dismiss { reason? }` — marks it dismissed.

### 6.6 Conflicts

Uploading a whole season in one shot can produce hundreds of rows that can't be placed as written. They aren't import
issues (the data is fine) — they are **claims**: *this occupant wanted this berth on these days*. Table `conflict`
(`0003_conflicts.sql`): the claim as the file stated it, its `type`, and a status `staged → open → placed | dismissed`.
Staged conflicts belong to a previewed import (discard deletes them); commit opens them on the project's **Conflicts** tab.

- **Blockers are computed on read**, never stored: one query per page joins each `OVERLAP` / `VESSEL_DOUBLE_BERTHED`
  conflict to the confirmed bookings in its way now. Cancel a blocker and the conflict shows "nothing in the way".
- **Place** (`action: "place", berthId, startDate?, endDate?, vesselLengthFt?`) runs the normal create path
  (`insertBooking`, `source: "import"`), so a still-blocked berth is the usual 409/422 and the conflict stays open.
- **Dismiss** one (with a reason), or in bulk: given ids, or every open conflict of one type.
- **Cloning** a template copies its open conflicts, so the sample project arrives with a real Conflicts tab
  (the sample workbook gives 282: ~240 `NO_BERTH`, ~29 `VESSEL_TOO_LONG`, a dozen `VESSEL_DOUBLE_BERTHED`, 1 `OVERLAP`).

**Later: CP-SAT.** The table is the solver's input as-is. Variables: for each open conflict *c* and each active berth
*b*, a boolean `x[c,b]` (plus, optionally, a small day shift). Hard constraints = the same rules: length fit (drop
`x[c,b]` where the vessel is too long), no two claims on an exclusive berth on the same day (`AddNoOverlap` over
optional intervals, with confirmed bookings as fixed intervals), one berth per vessel per day. Objective: maximise
placed claims, penalise moving off the requested berth and shifting days. Output = a list of proposed `place` actions
the user reviews and applies — the solver proposes, the rules still decide.

**Expected result on the provided sample** (from `data_analysis/stats.py`; use as a golden-test range, not exact): ~2,400 bookings parsed, ~300 `NO_BERTH`, ~104 `ANNOTATION_SKIPPED`, ~89 `OUTSIDE_MONTH_COLUMNS`, 3 `DUPLICATE_CARRYOVER`, 2 `HEADER_YEAR_MISMATCH` blocks (2010), ~498 vessels.

## 7. Audit

`GET …/audit` loads the project's all confirmed bookings and re-runs R1–R4 with the same code path — sort per berth and per vessel, compare neighbours (O(n log n); trivial at this size) — and returns an `AuditReport`.
On a healthy database `violations` is empty. That emptiness is the guarantee: the triggers make it so, the audit proves it, and it catches anyone who edited the database by hand.

## 8. Concurrency

**Assumption for v1: one user (the dock coordinator), one tab at a time.** Nothing below is built yet except `version`.

Each write is one Postgres transaction at `READ COMMITTED`. The service checks first (for good messages), then writes.
The constraints are the backstop if anything slips between the two.
Optimistic concurrency is only for *humans*: `UPDATE booking SET …, version = version + 1 WHERE id = ? AND version = ?`; zero rows changed → 409 `STALE_VERSION`.
Keep it even with one user: it also catches two open tabs.

### Later: many users (design only, not built)

**No application queue.** "First pushed wins" is what the database already does. With Postgres, a second transaction whose
range overlaps an uncommitted one waits on the `EXCLUDE` index. It fails with `23P01 exclusion_violation` once the first commits.
So the order is commit order, and writes to *different* berths never wait on each other. An app-level queue would add:
- Redis and a worker. An in-memory queue breaks as soon as there are two server instances, e.g. serverless.
- Async "queued" responses the UI has to poll.
- A single line that serializes unrelated writes.

The one place a lock *is* warranted is the import commit. It is long and touches every berth, so it takes `pg_advisory_xact_lock(<import key>)`.

| Race | Covered by | Gap |
|---|---|---|
| Two overlapping bookings on one berth (R2) | `EXCLUDE` constraint | — |
| One vessel booked in two places (R4) | `EXCLUDE` constraint | — |
| Two edits to the same booking | `version` → `STALE_VERSION` | — |
| Booking insert vs. vessel-length edit (R3/R6) | trigger checks | **Write skew.** Each transaction checks a snapshot the other is about to change. Fix: both paths lock the vessel row (and berth row) with `SELECT … FOR UPDATE` before checking, or run at `SERIALIZABLE` and retry. |

**Rejection log.** Every rejected write is recorded in `write_rejection` (see database.md §10) with:
- the operation and the payload attempted;
- the violation code and the conflicting booking;
- `lost_race`: the client sends `seenAt`, the time it loaded the data it validated against. If the conflicting booking's
  `created_at > seenAt`, it did not exist when the user looked. The message then reads "Taken N seconds ago by another booking",
  not "Already booked: …".

The rejected transaction has rolled back, so the log row is inserted **after** the rollback, as its own statement.
If it were inserted inside the transaction, it would vanish with it.

## 9. Seed data: the two templates

`npm run db:seed` builds two **template projects** (read-only; users get clones, infrastructure.md §2 and §4):

- **`defaults`**: the berths and vessels in `backend/seed/defaults.json`, no bookings.
- **`sample`**: a clone of `defaults`, plus the sample workbook run through the real importer (preview → commit, with
  every issue left open for triage), plus `as_of_date = 2019-07-01`.

Seeding is idempotent, and `--force` rebuilds both templates. User projects are never touched by a re-seed.

## 10. Test plan

- **Table-driven** — every row of the worked-examples table in manual.md becomes a test on `validateBooking`. The same cases run against the database directly in `db/schema.test.mjs` (36 cases, all passing).
- **Property test** — insert thousands of random bookings through the service; afterwards `audit` must be empty and every rejected booking must have named a real conflicting id.
- **Concurrency** — two `PATCH`es with the same `expectedVersion`: exactly one succeeds.
- **Seed** — the `defaults` template has exactly the berths and vessels in `defaults.json`. The `sample` template lands in the golden ranges of §6. Cloning either one gives equal counts and no row pointing back at the template.
- **Projects** — a write to a template → 403; project A's berth id used in project B → 404 (the service) or FK error (the DB); deleting a project leaves no rows behind.
- **Template import** — each issue code on a small hand-made file; an empty project plus the template file → a working project.
- **Delete** — a berth/vessel with a cancelled booking still can't be deleted; with none, it can.
- **Import golden test** — sample workbook lands in the ranges above; importing it twice yields zero new bookings; commit twice → 409.
- **Dates** — leap day, month/year boundaries, `2026-02-30` rejected, `startDate === endDate` (one-day booking).
